Vessel 0.3.1 adds observed position leverage, an Activity-based sizing record
when no closed Play outcome exists, and faster API startup and Activity reads.

## Highlights

- Activity shows venue-reported leverage for open and closed operations, with
  the latest observed value and its range. RISEx fills and retained refresh
  observations supply the data; unknown or conflicting latest values stay
  unknown. Leverage is never inferred from margin, notional or venue limits.
- Sizing suggestions can start from complete closed Activity operations,
  labelled **From Activity**, while no closed Play/manual outcome is decided.
  Activity and Play records are never mixed, and retrospective R stays unknown.
- API/worker images use ReadyToRun compilation. A bounded, read-only API warm-up
  prepares common reads before readiness, and cookie authentication uses fewer
  database reads while retaining revocation checks on every request.
- Activity reuses bounded, owner-scoped aggregates until a database facts
  revision changes. Commit-ordered invalidation covers executions, leverage,
  account settings and related facts. Authorization is never cached.
- Play account selection uses the shared searchable account picker.
- Play entry notional is summed exactly before conversion. Review and sizing
  exclude results that exceed exact decimal precision instead of rounding them
  into a different return.

Release workflows now use Blacksmith in
[`sloppitty/vessel`](https://github.com/sloppitty/vessel). Docker images remain
in the existing `skorcius/vessel` repository.

## Upgrading from 0.3.0

1. Stop web, API and all worker instances on every host, including
   `worker-notifications`. Back up both database schemas, evidence and credential
   keys and verify that the previous installation can be restored.
2. Set `VESSEL_VERSION=0.3.1`. Preserve the owner GUID and your selected storage,
   credentials, authentication and TLS overlays; use the matching API and web
   versions. Both workers use the API image.
3. Run the explicit one-shot `migrate` service before starting the upgraded
   hosts. It validates configuration, runs identity then journal bundles,
   bootstraps the owner and provisions messaging. Nothing migrates at startup.

| New journal migration | Effect |
| --- | --- |
| `20261018180202_LeverageObservations` | Retains observed leverage, adds nullable fill leverage and backfills current leveraged snapshot positions. |
| `20261019100000_ActivityFactsRevision` | Adds per-owner revision counters and commit-deferred invalidation triggers for the Activity cache. |

There is no new identity migration. Historical leverage is not reconstructed.
Disposable databases using the unshipped
`20261018130000_ActivityFactsRevision` ID must be recreated; never rename applied
migration-history records. Rollback requires the pre-upgrade backup and matching
old images, not down migrations.

For an upgrade from v0.2.0 or earlier, the v0.3.0 **order-identity restriction
still applies**: imported orders, fills or Play order links prevent an in-place
upgrade. Preserve a verified backup and use a deliberately fresh installation;
do not bypass the migration guard or clear individual tables. Follow the
[deployment runbook](https://github.com/sloppitty/vessel/blob/v0.3.1/deploy/README.md#from-v030-to-v031).

## Known limits

- Hyperliquid and Lighter executions do not provide usable leverage; their
  Activity leverage depends on retained observations. Incomplete or ambiguous
  observations remain unknown and never determine operation grouping.
- The Activity sizing fallback excludes incomplete executions/fees, out-of-range
  returns and entry notionals beyond exact precision. It does not create Plays
  or execution links. Suggestions remain estimates, not advice.
- API warm-up defaults to 30 seconds and is limited to 60 seconds. Failure or
  timeout releases the warm-up gate; normal database/migration readiness checks
  still apply. The Activity cache is bounded and does not survive restarts.
- Wallet sign-in remains opt-in. Real-wallet acceptance is owner-pending;
  registration stays `Closed`. Funding remains separate from execution net
  while its PnL basis is unknown.
