Vessel health review

The foundations are better than I expected from six weeks of agent-written code. The part you care about most, the numbers, is where I found the real defects. This report says what to keep, what to fix first, what to simplify, and what I already changed.

Verdict

Vessel is in good shape where discipline was written down early. Amounts stay exact decimals from the venue to the screen. Every table is filtered by owner, and the model refuses to build without that filter. Venue reads are bounded and strict. Lease fencing in the monitor is correct. Two independent security audits, one from Claude and one from Sol, found no critical or high issue.

The weak points are the ones that matter for a tool you will use to judge your own trading.

1. Some numbers are wrong or disagree

Each calculation is tested alone with hand-computed values. Nothing checks that Overview, Activity and Review agree on one dataset, and they do not. I read the code behind the main defects, and a second model then tried to refute them. Most held.

Numbers

2. Protection checks fail quietly

One history gap, or one open order the adapter cannot read, turns off stop checks for the whole account. You get a single "degraded" warning and then silence, including for Plays opened weeks later.

Protection

3. Nothing verifies main

CI runs only on release tags. Locally, 827 of 2,269 backend tests skip without a database variable and check.sh still reports green. Eight releases shipped in 19 days on that basis.

Agents and releases

4. Some complexity has not paid for itself

RabbitMQ and Wolverine carry events that PostgreSQL already stores and replays. Trading mode is a string passed through 30 defaulted parameters. Five services are over 800 lines.

My opinion

Stop adding features for two or three weeks. Build one hand-checked "golden journal" dataset, assert every screen against it, and fix what it exposes. That one fixture would have caught most of the number defects below, and it protects every later refactor. Then cut the messaging stack down, because it is the largest piece of code and operations that buys you nothing today.

Tried and reverted

Three of my changes did not survive verification. I count that as the process working.

  • Tie-break between the sizing window and the exposure ladder. A use-case test failed, and it pins a documented decision ("ties are disclosed, not ordered", decision 7). Now N-16, a decision for you.
  • An unconditional HSTS header in the Caddyfile. The Sol review pointed out that the documented localhost test setup with Caddy's internal CA would pin HTTPS on localhost for a year, on every port. It needs to be opt-in. Now Q-20.

Why the test suite missed these

The suite is large and mostly honest. Expected values are hand-computed literals, not recomputed with the code under test. Fee handling on both bases, flips, exact sums and the manual ledger are well covered. Four things let the defects through.

No test loads one dataset through two screens

Overview, Activity and Review each pass their own tests. Two of those tests pin opposite window edges, and both are green.

Fixtures are long, one unit, two fills

Review metrics are never computed for a short Play. Flipping the short branch of the initial-risk check fails no test. Open risk has one short case.

Some figures are never asserted

AverageR has no assertion anywhere. The snapshot guards of unrealized P&L are untested. "Scratches do not break streaks" has no win, scratch, win case.

A third of the suite skips silently

827 of 2,269 test methods need the test database (12 of them the broker too). Without Vessel_TEST_POSTGRES they skip, check.sh still passes, and CI runs only on tags.

Proposal: a golden journal

One small dataset, checked by hand once, loaded once, asserted through Activity, Overview, Review, Sizing and Open risk at a fixed clock. Two accounts on different P&L bases, one disabled account with a large win, a long with exit-then-add, a short, an exact-zero scratch between two wins, a fee-only loss, an unlisted fee token, a flip, an order with a known missing execution, an open position with a supplied mark, two closes at the same instant and one exactly on the 7-day boundary.

Then assert identities, not only values. Overview realized equals the sum of Activity's closed nets for the scope. Review net with positions included equals Overview realized minus a listed set of exclusions. Group nets sum to the total. Two days of work, and N-1, N-4, N-15 and N-21 can no longer pass unnoticed.

You rely on Vessel to tell you when a live position is not protected the way the plan says. The mechanics are careful. Nothing resolves on a failed read, a candidate needs two observations a minute apart, the grace period counts from the first entry fill and never restarts, and wrong-side stops never count as protection. The problem is what happens when the monitor is unsure.

Big improvements

Six pieces of work that change how safe or how cheap Vessel is to run. Each needs your agreement before anyone starts.

B-1. A golden journal and a cheap check on main

Described under numbers. Pair it with the smallest CI that respects your runner budget: a path-filtered job on pull requests that runs typecheck, lint, vitest, the build and the Unit and UseCases tests with no services. That is 6 to 9 minutes on the current runner. Add a local pre-push hook that runs a changed-files subset. The history since you restricted CI shows the cost of not having it: about 700 commits and 8 releases in 19 days (0.3.1 to 0.4.2), about 160 of those commits being fixes or test repairs, and one smoke-test fix that landed inside a release pull request.

B-2. An Activity read model

Activity, the Overview summary, row expansion and a Play's funding all read one in-memory aggregate of every retained fill. It is cached by a "facts revision" that database triggers bump. Two things work against it as history grows. Every monitor check that saves a newer snapshot bumps the revision, even when quantities and money are unchanged, so with several monitored accounts many visits are a cache miss. And an entry larger than the cache capacity (256 MiB by default, configurable) is never stored, so every request recomputes. The repository has two measurements: about 128 MiB charged at 46k fills in one benchmark and 165 MiB at 100k fills plus 40k funding rows in another. The limit is therefore crossed somewhere between roughly 90k and 155k fills, depending on the shape of your data. Review is not cached at all and already takes 1.6 s at 774 Plays.

Before the read model, three smaller steps buy time. Separate the snapshot-dependent checks from the execution aggregate, so a new observation time does not discard the expensive part. Snapshot freshness is a real input to the proofs, so do not simply ignore those writes. Store the sorted list and facets with the cached entry. Keep only the columns later reads need, not whole fill entities. Run scripts/benchmark.py --scale 4 first to confirm the cliff. It does not yet time /api/sizing, a Play's executions or realistic drawing sizes.

B-3. Cut the messaging stack down

In this design correctness already lives in PostgreSQL: events, receipts, the dispatcher, catch-up and retention. RabbitMQ only shortens latency from the 30-second catch-up to under a second for notifications, on checks that run every ten minutes. It costs about 1,100 lines in Vessel.Messaging, a broker container with its own users and password rotation, per-deployment Wolverine schemas, a provisioning step and a large part of the runbook. It is also a startup dependency of every host. If a host cannot start while the broker is down, a broker outage followed by a worker restart stops protection checks for everyone, although nothing they need is missing. The last point is unproven: a second reviewer could not confirm the startup failure by reading, and the October research note says that case was never tested. Write the cold-start test first.

My opinion

You chose RabbitMQ in October with external channels in mind. None exists, and decision 12 is deferred. I would remove the broker now and add it back the day a consumer outside the process needs it. If you keep it, make it a soft dependency so the monitor and the API start without it. One caveat: LISTEN/NOTIFY does not pass through a transaction-pooling proxy such as PgBouncer. The Compose deployment has none.

B-4. Publish the image you verified

The release workflow builds the images three times: once in each storage verification job and again in the publish job, on separate runners. The runtime bases float by tag (aspnet:10.0, nginx-unprivileged:alpine, node:24-bookworm-slim), so the bytes you ship were never the bytes you tested. There is also no test that upgrades from the previous release, although every upgrade you run does exactly that. The published bytes are not proven different. They are also not proven to be the tested ones.

B-5. An operator command for upgrades

The upgrade procedure is prose spread over about 1,700 lines and 17 per-version sections of a 98 KB runbook. The generic command block says "back up first" and then does not back up. The stop lists leave out the paper worker. The backup overwrites the previous one. Post-migration steps such as the search rebuild in 0.4.0 exist only inside version notes. I would replace the procedure with a deploy/vessel script: preflight, backup, upgrade --to X, restore --from DIR, status, rollback. Each step prints what it will do and needs --yes. A small docs/releases/vX.Y.Z.upgrade.json per release lists migrations, post-steps and config changes. verify-release.py then drives the script, so the procedure is tested on every release and safe for an agent to run.

B-6. One version handshake between web and API

The frontend guards carry 113 "field may be absent on older servers" checks and 60 comments about them. The backend always sends those fields. Nothing compares the two versions, so a tab left open across an upgrade fails with "incompatible workspace data" and no hint that a reload fixes it. Put the API version in /api/system, compare it on stream reconnect, show a "new version, reload" notice that respects unsaved work, and then delete the fallbacks.

Guardrails that do not depend on reading

Permission rules

A checked-in .claude/settings.json (and the Codex equivalent) that denies reading .env files, docker push, forced pushes, git tag -f and --tags.

A pre-tool hook

Block any command that combines the development database port with migrate, database update or psql, and any test run whose database variable points at the live database name.

A pre-push hook

Run the changed-files check. Refuse to push a v* tag unless release.py check --tag passes.

Repository settings

Branch protection requiring the fast job, a tag ruleset that forbids moving or deleting v*, and code owners on .github/, deploy/ and scripts/release.py.

My opinion

The upgrade skill and the operator script are one piece of work, and they are what "better deployment agents" means in practice. An agent with a tested vessel upgrade --to 0.4.3 cannot skip the backup or forget the paper worker. An agent with a 98 KB runbook can. Do that before any further skill.

What to keep and protect

These are the decisions that make the rest fixable. Any refactor that weakens one of them is a bad trade.

Exact numbers end to end

ExactDecimal and ExactAmount keep sums in 10⁻²⁸ units on big integers and round once. Venue JSON that a decimal cannot hold exactly is rejected. The browser formats the original string and uses BigInt for shares.

Owner isolation in depth

Every entity implements IOwned or the model refuses to build. A save guard rejects foreign rows. Raw SQL repeats the owner predicate. Workers open a scope per owner.

Unknown stays unknown

Open risk makes a whole Play unknown rather than partly summing it. Funding totals stay null without a verified basis. Division by zero is null, not zero.

Layering enforced by tests

Domain and Application have no package references. An architecture test fails the build on a wrong project reference. The frontend has the same for api, components and features.

Strict, bounded venue reads

One deadline per multi-request read, a byte cap while reading, duplicate-key rejection, fixed HTTPS hosts, no redirects, IDs never parsed as numbers.

Sign-in and the credential vault

Challenges are single-use even when they fail. Sessions are revalidated on every request. Three-layer CSRF defence. AES-GCM with the owner, account and purpose bound into the associated data.

Lease fencing and the event log

Every monitor write checks generation, holder and expiry under row locks. Venue reads run with no transaction open. Event sequences are allocated at commit, so order equals commit order.

The release script and the restore drill

release.py refuses to overwrite a version built from another commit and moves "latest" only after both images verify. verify-release.py restores a dump into fresh volumes on every release.

One transport in the browser

A single fetch wrapper owns timeouts, session-generation discard and safe error text. Pure static calculators on the backend are where logic is cheapest to test. Keep writing new logic that way.

The order I would do it in

Four passes. Each one makes the next cheaper. Nothing in the first two needs a migration of your live database except the two indexes.
